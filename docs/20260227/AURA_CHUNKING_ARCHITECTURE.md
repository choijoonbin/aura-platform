# Aura 지능형 청킹 아키텍처
### RAG 정답률을 결정하는 1차 통제 레이어

> **발표 대상**: PM · AI/RAG 엔지니어 · 운영 담당자

---

## 들어가며: 왜 청킹이 핵심인가

### 청킹이란 무엇인가

청킹(Chunking)은 PDF나 텍스트 문서를 **검색 가능한 조각(청크)으로 분할하는 작업**이다.

RAG(Retrieval-Augmented Generation) 시스템에서 AI가 답변을 생성하는 과정은 다음과 같다.

```
[사용자 질문]
  → ① 질문을 벡터(숫자)로 변환
  → ② 벡터 DB에서 가장 유사한 청크를 검색 (Top-K)
  → ③ 검색된 청크를 LLM에게 제공
  → ④ LLM이 청크를 읽고 답변 생성
  → [최종 답변]
```

이 흐름에서 **③에서 LLM에게 제공되는 청크의 품질**이 최종 답변 정확도를 결정한다.
아무리 좋은 LLM(GPT-4o)을 써도 엉터리 청크가 들어오면 엉터리 답변이 나온다.

### 청킹이 나쁘면 어떤 일이 생기나

| 문제 상황 | 결과 |
|-----------|------|
| 청크 경계가 잘못 잘림 | 검색은 됐는데 인용 근거가 엉뚱한 조항을 가리킴 |
| 메타데이터(조항 번호)가 없음 | 감사 추적 불가, 근거 맵이 무너짐 |
| 중복 청크가 많음 | Top-5 결과 중 3개가 같은 내용 → 답변 품질 저하 |
| 노이즈 청크(제목만 있는 청크) | LLM이 빈 내용을 읽고 "관련 정보 없음" 응답 |
| 컨텍스트 없이 조항만 있음 | LLM이 "제9조"를 읽어도 이게 여비 규정인지 인사 규정인지 모름 |

> **청킹은 저장 전처리가 아니라 판정 정확도의 1차 통제 레이어다.**

## 1부. 처음 시작 — 규칙 기반 청킹 (v1)

### 1.1 최초 전략: 정규식으로 자른다

처음 전략은 단순했다. 한국 규정집은 대부분 `제N장 / 제N조 / ① 항 / 가. 호` 구조를 따른다.  
이 패턴을 정규식으로 감지하고 경계마다 청크를 만드는 방식이다.

```
[입력 문서]
  제3장 여비
  제9조(여비의 종류) 이 규정에서 정하는 여비는 다음과 같다.
    ① 국내 출장비
    ② 해외 출장비
  제10조(지급 기준) ...

[v1 청킹 결과]
  청크 1: "제9조(여비의 종류) 이 규정에서 정하는 여비는..."
  청크 2: "제10조(지급 기준) ..."
```

**처리 흐름**

```
문서 등록
  → 텍스트 추출 (PDF → 순수 텍스트)
  → 정규식으로 장·조·항·호 경계 감지
  → 경계마다 청크 생성
  → 청크가 max_chars(800자)를 초과하면 추가로 분할
  → 각 청크를 임베딩 벡터로 변환
  → pgvector DB에 저장
```

**장점**
- LLM을 전혀 쓰지 않아서 빠르고 비용이 없다
- 표준 한국 규정 체계(제N조 방식)에서는 잘 작동한다
- 예측 가능하고 안정적이다

---

### 1.2 운영하면서 발견한 3가지 페인 포인트

#### 문제 ① 비표준 구조 — 정규식이 못 잡는 문서

회사마다 규정 문서의 구조가 다르다. 정규식은 미리 만들어둔 패턴만 인식한다.

```
[정규식이 잘 잡는 표준 패턴]
  제9조(여비의 종류)
  제10조(지급 기준)

[정규식이 못 잡는 비표준 패턴]
  3-1. 여비의 종류    ← 숫자-숫자 형식, 정규식 미감지
  Ⅱ. 지급 기준       ← 로마자 체계, 파싱 실패
  2.1.1 적용 범위    ← 소수점 계층 구조, 인식 불가
```

정규식이 경계를 못 찾으면 문서 전체가 청크 하나가 된다.  
이 거대한 청크 하나가 LLM 컨텍스트 윈도우(4,096 토큰)를 초과하면 검색 자체가 불가능해진다.

#### 문제 ② 컨텍스트 단절 — "이게 어느 규정 청크야?"

정규식은 조항 텍스트만 자를 뿐, 그 조항이 **어느 장에 속하는지, 문서가 전체적으로 무슨 내용인지** 정보를 청크에 넣지 않는다.

```
[검색으로 가져온 청크]
─────────────────────────────────────────
제9조 ② 출장 시 일비는 다음과 같이 지급한다.
  가. 국내 출장: 1일 30,000원
  나. 해외 출장: 1일 50달러
─────────────────────────────────────────
```

LLM이 이 청크만 보면 판단할 수가 없다.
- 이게 "여비 규정"의 제9조인지, "복리후생 규정"의 제9조인지 알 수 없다
- 이 조항이 어느 장에 속하는지 알 수 없다
- 문서 전체 맥락에서 이 조항이 어떤 의미인지 알 수 없다

결과적으로 LLM이 조항 번호가 같은 다른 규정의 내용과 혼동하거나, 맥락 없이 숫자만 인용하는 오류가 발생한다.

#### 문제 ③ 기계적 분할 — 크기 기준으로 자르면 의미가 끊어진다

긴 조항(800자 초과)을 크기만 보고 자르면 두 가지 문제가 동시에 발생한다.

```
[제24조 접대비 규정이 800자를 초과할 경우]

청크 A: "제24조(접대비/업무추진비) ① 접대비란 거래처 및 관련자와의
         업무 관련 식사, 선물 등에 사용하는 비용이다.
         ② 1인당 지출 한도는 30만원이며, 증빙 서류는 반드시"

청크 B: "법인카드 영수증을 제출해야 한다.
         제25조(출장비) ① 출장비는 교통비·숙박비·일비·식비로 구성된다."
```

- 청크 A: 제24조 내용이 잘려서 의미 단절
- 청크 B: 제24조 끝 + 제25조 시작이 섞임
- "법인카드 영수증 제출" 규정이 어느 조항 것인지 추적 불가

---

### 1.3 v1 실측 결과 — 얼마나 문제였나

동일 문서(61개 조항, 약 14,000자 경비 지출 규정)를 v1으로 청킹한 결과:

```
품질 측정 결과 (v1)
──────────────────────────────────────────────────────────
  최종 청크 수:                          77개
  조항 번호 보유율 (article_coverage):   ~82%  ← 18% 조항 번호 없음
  저정보 청크 비율 (short_chunk_rate):   ~17%  ← 제목만 있는 빈 청크
  컨텍스트(상위 경로) 주입:              없음
  메타데이터 자동 보강:                  없음
  자기교정:                              없음
──────────────────────────────────────────────────────────
```

**해석**
- 조항 번호 18% 누락 = 검색 결과에서 근거 조항을 18% 확률로 추적 불가
- 저정보 청크 17% = 77개 중 13개는 "제3장", "부칙" 같은 제목만 있는 쓸모없는 청크
- 이 쓸모없는 청크들이 Top-K 검색 결과를 오염시킴

## 2부. 고도화 — 에이전트형 청킹 v2

### 2.1 설계 원칙의 전환: 규칙에서 AI로

v1의 핵심 한계는 **"규정 문서가 어떻게 생겼을지를 미리 가정"** 한다는 것이다.
정규식은 개발자가 예상한 패턴 외에는 아무것도 못 한다.

v2의 핵심 아이디어는 하나다.

> **청킹 전에 AI가 먼저 문서를 읽고, 이 문서에 맞는 청킹 전략을 스스로 결정하게 한다.**

```
v1 철학: "문서는 이렇게 생겼을 것이다 → 이 규칙으로 자른다"
v2 철학: "문서를 먼저 읽어라 → 이 문서에 맞는 방법으로 자른다"
```

---

### 2.2 v2 전체 파이프라인 — 5단계 흐름

문서 하나가 들어왔을 때 v2가 처리하는 전체 흐름이다.

```
┌─────────────────────────────────────────────────────────────────────┐
│                       Agentic Chunking v2                            │
│                                                                      │
│  [문서 입력]                                                          │
│      ↓                                                               │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ Step 1: 문서 프로파일링 (LLM이 먼저 읽는다)                  │    │
│  │   → 구조 유형 판단 / 청킹 전략 결정 / 문서 요약 생성         │    │
│  └─────────────────────────────────────────────────────────────┘    │
│      ↓ "이 문서는 계층형 한국 규정, 이 앵커로 자른다"                 │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ Step 2: 하이브리드 청킹                                      │    │
│  │   → 레이아웃 보호(표/리스트) + 전략별 분할 + 의미 세분화     │    │
│  └─────────────────────────────────────────────────────────────┘    │
│      ↓ 1차 청크 생성 완료                                            │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ Step 3: 컨텍스트 보강                                        │    │
│  │   → 모든 청크에 [문서 요약 + 경로] 텍스트 삽입              │    │
│  │   → 약한 메타데이터 LLM으로 채움                            │    │
│  └─────────────────────────────────────────────────────────────┘    │
│      ↓ 청크에 맥락 정보 추가됨                                       │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ Step 4: 자기교정 루프 (LLM이 청크 전체를 재검토)             │    │
│  │   → 의미 단절 청크 → 병합 / 조항 혼재 청크 → 분할           │    │
│  └─────────────────────────────────────────────────────────────┘    │
│      ↓ 교정 완료                                                     │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ Feedback Loop: 품질 피드백                                   │    │
│  │   → LLM이 샘플 청크의 RAG 적합성 평가                       │    │
│  │   → "poor" 판정 청크 추가 병합                              │    │
│  └─────────────────────────────────────────────────────────────┘    │
│      ↓                                                               │
│  [최종 청크 → 임베딩 → pgvector 저장]                                │
└─────────────────────────────────────────────────────────────────────┘
```

---

### Step 1 — 문서 프로파일링: AI가 먼저 읽는다

**무엇을 하나**

청킹 시작 전, LLM(GPT-4o-mini)이 문서의 첫 2,000자를 읽고 4가지를 판단한다.

| 판단 항목 | 의미 | 예시 결과 |
|-----------|------|-----------|
| **구조 유형** | 이 문서가 어떤 체계로 구성됐나 | `standard_korean_regulation` (표준 제N조) / `numbered_outline` (1.1.1 체계) |
| **문서 성격** | 어떤 종류의 문서인가 | `regulation` (규정) / `manual` (매뉴얼) / `guideline` (지침) |
| **청킹 전략** | 어떤 방법으로 자를 것인가 | `hierarchical` / `outline` / `semantic` |
| **문서 요약** | 이 문서가 전체적으로 무슨 내용인가 | "회사 경비 지출 관리 및 SAP 전표 검증 기준을 정의하는 규정" |
| **커스텀 앵커** | 이 문서 고유의 구분자 패턴 | `['제1장', '제1조', '제2장']` |

**왜 중요한가**

정규식은 `제N조` 패턴만 알고 있지만, LLM은 문서를 읽고 어떤 패턴으로 구성됐는지 파악한다.  
비표준 문서(3-1 체계, 로마자 체계, 소수점 체계)도 LLM이 "아, 이 문서는 이런 식으로 나뉘어 있구나"를 스스로 파악하고 그에 맞는 전략을 선택한다.

**실제 테스트 로그 (경비지출관리규정 v2.0 처리 시)**

```
LLM 프로파일링 결과:
  structure_type = "standard_korean_regulation"
  doc_character  = "regulation"
  strategy       = "hierarchical"
  anchors        = ['제1장', '제1조', '제2장', '제3조', '제4조']
  summary        = "이 문서는 회사의 경비 지출 관리 및 관련 규정을 정의하며,
                    SAP 전표 검증과 재무 리스크 통제를 위한 기준을 제시한다."
```

---

### Step 2 — 하이브리드 청킹: 규칙 + 의미 + 레이아웃 보호

프로파일링에서 결정된 전략을 기반으로 실제 청킹을 수행한다.  
세 가지 기술이 결합된다.

#### ① 레이아웃 보호 (표·리스트 블록이 잘리지 않게)

규정집에는 표(Table)와 리스트가 많다. 기계적으로 800자씩 자르면 표 중간이 잘린다.

```
[잘못 잘린 표]
청크 A: "...지급 기준은 다음과 같다.
         ┌──────────┬──────────┐
         │ 직급      │ 한도      │
         ├──────────┼──────────┤
         │ 부장      │ 50만원    │"

청크 B: "│ 과장      │ 30만원    │
         └──────────┴──────────┘"
```

레이아웃 보호는 표와 리스트 블록을 미리 감지하여 특수 마커로 감싼다.  
청킹 알고리즘이 이 마커를 인식하여 블록 내부에서 자르지 않는다.

**실제 처리 로그**: `표=0 리스트=48 감지/보호` (경비규정에 리스트 48개 보호됨)

#### ② 전략별 분할

Step 1에서 결정된 전략에 따라 다른 방법으로 자른다.

| 전략 | 적용 대상 | 방법 |
|------|-----------|------|
| `hierarchical` | 표준 한국 규정 | 제N장/제N조/항/호 경계로 분할 |
| `outline` | 1.1.1 / 로마자 체계 | LLM이 발견한 커스텀 앵커로 분할 |
| `semantic` | 자유 형식 문서 | 임베딩 유사도로 주제 변화 지점 탐지 |

#### ③ 의미 기반 세분화 (Semantic Hybrid Sub-chunking)

1차 분할 후 생성된 청크가 여전히 너무 크면(예: 긴 제9조 전체가 하나의 청크),  
그 청크 내부에서 임베딩 유사도를 계산하여 주제가 바뀌는 지점을 찾아 추가로 자른다.

```
[1차 분할 결과 - 제9조가 1,200자로 큼]
  → 문장 간 임베딩 유사도 계산
  → "식대 지급 기준" / "교통비 지급 기준" / "숙박비 지급 기준" 경계 감지
  → 3개 청크로 추가 분할
```

글자 수가 아닌 **의미 변화 지점**에서 자르므로 청크 내 내용이 훨씬 일관적이다.

### Step 3 — 컨텍스트 보강: 모든 청크에 "길 안내" 삽입

**핵심 아이디어: Small-to-Big (Contextual Retrieval)**

v1의 문제 중 하나가 "조항만 있고 맥락이 없다"는 것이었다.  
v2는 이를 해결하기 위해 모든 청크 본문 맨 앞에 상위 컨텍스트를 **텍스트로 직접 삽입**한다.  
메타데이터 필드가 아닌, 실제 검색되는 텍스트 본문에 삽입하는 게 핵심이다.

```
[Step 3 이전]
─────────────────────────────────────────────────────
② 출장 시 일비는 다음과 같이 지급한다.
  가. 국내 출장: 1일 30,000원
  나. 해외 출장: 1일 50달러
─────────────────────────────────────────────────────

[Step 3 이후]
─────────────────────────────────────────────────────
[문서 요약: 이 문서는 회사의 경비 지출 관리 및 SAP 전표 검증과
재무 리스크 통제를 위한 기준을 정의한다.]
[경로: 제4장(출장비 규정) > 제25조(출장비)]

② 출장 시 일비는 다음과 같이 지급한다.
  가. 국내 출장: 1일 30,000원
  나. 해외 출장: 1일 50달러
─────────────────────────────────────────────────────
```

**왜 메타데이터가 아닌 텍스트 본문에 넣나**

벡터 검색은 **텍스트를 임베딩**하여 검색한다.  
메타데이터는 필터링에 쓰이지, 임베딩 벡터에 포함되지 않는다.  
"출장비 규정"으로 검색할 때, 이 문서가 경비지출규정이라는 정보가 벡터에 녹아 있어야  
"제25조 일비" 청크와 유사도가 높게 계산된다.

**효과**: Anthropic 연구 기준 RAG 검색 정확도 35~50% 향상.  
LLM이 조항 하나만 읽어도 "어느 문서의 어느 장에 속한 내용"인지 즉시 파악 가능.

---

### Step 4 — 자기교정 루프: LLM이 직접 청크를 수술한다

**무엇을 하나**

Step 2~3으로 생성된 전체 청크 목록을 LLM이 처음부터 끝까지 검토한다.  
"이 청크와 다음 청크가 이어지는 내용이면 합쳐라", "이 청크에 두 조항이 섞여 있으면 나눠라" 판단을 내리고, 실제로 적용한다.

**실제 교정 사례 (오늘 실행 테스트 결과)**

```
[병합(Merge) 판단 - 12건 적용]
  "제7장 제목만 있고 제23조 내용이 이어지기 때문에 병합이 필요함"
   → 제7장 제목 청크 + 제23조 내용 청크를 하나로 합침

  "제24조 내용이 끝나지 않고 제25조로 넘어가는 관계로 병합이 필요함"
   → 잘린 제24조를 다시 이어 붙임

  "두 청크가 동일 조항(제3조)에 속하며 내용이 너무 짧아 독립성이 없음"
   → 같은 조항이 두 개로 쪼개진 것을 하나로 합침

  "제12조와 제13조가 연속적인 내용으로 연결되어 있음"
   → 맥락상 이어지는 두 조항을 합침

[분할(Split) 판단 - 1건 감지]
  "하나의 청크에 두 개 조항의 핵심 내용이 섞여 있음 → 분할 필요"
   → 한 청크에 섞인 내용을 두 청크로 분리
```

**처리 전후 수치**
```
  자기교정 전: 78개 청크
  병합 12건 적용
  분할 1건 적용
  자기교정 후: 67개 청크
```

**LLM이 이 판단을 어떻게 하나**

각 청크의 첫 문장과 마지막 문장을 LLM에게 제공하면, LLM이 문맥을 읽고  
"다음 청크가 이 내용의 연속인지", "이 청크가 하나의 완결된 의미 단위인지"를 판단한다.  
이것이 정규식으로는 절대 할 수 없는 **의미론적 판단**이다.

- 결과: Top-K 검색에서 쓸모없는 청크가 자리를 차지하지 않음 → 정밀도 향상

### 2.4 실시간 Score 피드백 루프 — 실제 검색 결과로 품질을 측정한다

**문제 인식**

청킹 품질을 LLM이 평가하는 방식(Step 4 Feedback)은 주관적이다.  
"이 청크가 잘 만들어진 것 같다"는 LLM의 판단이지, 실제로 사용자 검색에서 잘 찾히는지는 알 수 없다.

**해결 방법: 실제 검색 점수를 추적한다**

pgvector는 검색 결과마다 **코사인 유사도 점수(score, 0~1)**를 반환한다.  
score가 높을수록 쿼리와 청크가 잘 매칭된다는 의미다.

v2는 이 점수를 Redis에 문서별로 누적하여, 점수가 지속적으로 낮은 문서를 자동으로 재청킹한다.

**전체 동작 흐름**

```
[사용자가 검색을 실행]
  → pgvector가 유사도 점수(score)를 반환
  → 각 검색 결과의 doc_id와 score를 Redis에 자동 기록
     (Redis Key: rag:score_stats:{doc_id})
     (저장 내용: 누적 검색 횟수, 누적 총점)
  → 누적 횟수 ≥ 5회 도달 시 롤링 평균 계산
  → 평균 score < 0.65 (임계값) 이면 재청킹 필요로 판단
  → Redis 재청킹 큐에 해당 doc_id 등록
     (Key: rag:reindex_queue)
  → 백그라운드 워커가 30초마다 큐를 확인
  → 큐에 항목 있으면 → v2 재청킹 자동 실행
  → 재청킹 완료 → Redis 통계 초기화 → 새 기준으로 재측정 시작
```

**핵심 가치**

- LLM 주관 평가가 아닌 **실제 사용자 검색 행위 기반** 객관적 품질 측정
- 운영팀 개입 없이 품질 저하 문서를 **자동 감지 → 자동 복구**
- 재청킹 후 효과도 같은 방법으로 측정 가능 (개선 전후 score 비교)

**설정값 (환경변수로 조정 가능)**

```
RAG_SCORE_TRACKING_ENABLED=true     # 추적 활성화 여부
RAG_SCORE_AVG_THRESHOLD=0.65        # 이 점수 미만이면 재청킹 판단
RAG_SCORE_MIN_SEARCHES_BEFORE_REINDEX=5  # 최소 5회 검색 후 판정 (1~2회 이상치 방지)
RAG_SCORE_WORKER_POLL_SECONDS=30    # 워커가 30초마다 큐 확인
```

### 2.5 Query Rewriter — 검색 입력단 강화

**문제 인식**

청킹이 완벽해도, 검색 쿼리 자체가 엉터리이면 결과가 0건이다.

우리 시스템에서 검색 쿼리는 두 가지 경로로 들어온다.
1. 사용자가 직접 입력하는 자연어 질문: "출장비 일비 기준이 뭐야?"
2. 에이전트가 자동으로 생성하는 쿼리: SAP 전표 분석 중 "PA0030 처리 기준 조회"

특히 2번 경우, SAP 코드값이나 시스템 내부 코드가 그대로 쿼리로 들어오면 벡터 DB에서 매칭되는 텍스트를 찾지 못한다. 규정집에는 "PA0030"이라는 단어가 없고 "복리후생비"라고 적혀 있기 때문이다.

**해결 방법: 벡터 검색 직전 쿼리를 자동으로 변환**

```
[변환 전 → 변환 후] (실제 테스트 결과)

"PA0030 식대 처리"    → "복리후생비/식대 처리 규정 및 지출 기준"
"법카 사용 기준?"     → "법인카드 사용 기준 및 승인 절차"
"SAP 6311 한도"      → "접대비/업무추진비 지출 한도 기준 및 승인 절차"
"출장정산 어떻게"     → "출장비 정산 절차는 어떻게 되나요?"
```

**동작 원리와 비용 최적화**

모든 쿼리를 LLM으로 변환하면 비용이 너무 많이 든다.  
그래서 **쿼리를 먼저 검사하여 변환이 필요한 것만 LLM을 호출**한다.

```
쿼리 입력
  ↓
[휴리스틱 검사] — 아래 조건 중 하나라도 해당하면 변환 필요로 판단
  · 대문자+숫자 조합 (PA0030, SK0100 등 SAP 코드)
  · 4자리 이상 숫자 단독 (GL 코드 6311 등)
  · 대문자 약어 (SAP, ERP, GL 등)
  · 알려진 줄임말 포함 (법카, 출장정산 등)
  · 쿼리 길이 8자 이하
  NO → 그대로 벡터 검색 (LLM 호출 없음, 추가 비용 0원)
  YES ↓
[LLM 변환] — GPT-4o-mini가 의미어로 확장
  + LRU 캐시(256개) 적용 → 같은 쿼리는 한 번만 변환
  ↓
재작성된 쿼리로 벡터 검색
  검색 결과 있음 → 반환
  0건 ↓
원본 쿼리로 재시도 (안전망 — 변환이 오히려 나빴을 경우 대비)
  ↓
기존 키워드 폴백 검색
```

**"접대비 법인카드 사용 의무"처럼 이미 명확한 한국어 쿼리는 LLM을 전혀 호출하지 않는다.**  
비용은 실제로 변환이 필요한 코드값/줄임말 쿼리에만 발생한다.

운영팀이 이 화면에서 "재청킹 필요" 문서를 클릭하면 수동 재청킹을 바로 실행할 수 있다.

---

### ⬜ 예정: 골든셋 기반 자동 평가

**무엇인가**

"청킹을 바꿨더니 실제로 검색 정확도가 좋아졌나?"를 자동으로 측정하는 시스템이다.

**방법**

미리 정답을 알고 있는 QA 쌍(골든셋)을 만들어둔다.

```
골든셋 예시:
  Q: "접대비 1인당 한도는 얼마인가?"  → A_조항: 제24조 ②
  Q: "출장 국내 일비 기준?"            → A_조항: 제25조 ②가
  Q: "법인카드 필수 사용 규정?"         → A_조항: 제14조 ①
```

청킹이나 검색 로직이 변경될 때마다, 이 골든셋 질문들로 자동 검색을 실행하여 정답 조항이 Top-3 안에 들어오는 비율을 측정한다.

```
배포 전 자동 평가 게이트:
  골든셋 50문항 검색 실행
  → 정답 Top-3 히트율 85% 이상 → 배포 승인
  → 히트율 85% 미만 → 배포 차단, 알람 발송
```

**이것이 완성되면**: 청킹 알고리즘을 수정할 때마다 "실제로 나빠졌는지"를 수동 테스트 없이 자동으로 검증할 수 있다.

## 결론

> **"Aura의 청킹은 단순한 텍스트 분할이 아닙니다.**
> **AI가 문서를 이해하고 전략을 결정하며, 결과를 스스로 교정하고,**
> **실제 검색 품질로 지속적으로 개선하는 자율 품질 관리 계층입니다."**

**한 문장 요약**: 문서가 들어오면 AI가 스스로 최적 청킹 전략을 결정하고, 잘못 잘린 청크를 직접 수술하며, 이후 실제 검색 성과를 추적해서 품질이 떨어지면 스스로 재청킹을 실행한다.

| 단계 | 핵심 변화 | 상태 |
|------|-----------|------|
| v1 (규칙 기반) | 정규식으로 빠르게 자른다 | ✅ 운영 중 (폴백으로 활용) |
| v2 (에이전트형) | AI가 문서를 읽고 스스로 전략을 결정 | ✅ 적용 완료 |
| Score 피드백 루프 | 실검색 점수로 자동 품질 감시·재청킹 | ✅ 적용 완료 |
| Query Rewriter | 코드값·줄임말을 검색 전 자동 변환 | ✅ 적용 완료 |
| 품질 대시보드 | 문서별 score를 화면에서 모니터링 | ⬜ BE/FE 연동 계획 중 |
| 골든셋 자동 평가 | 변경 시마다 정확도 자동 검증 | ⬜ 계획 중 |
